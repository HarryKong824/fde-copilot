# 核心 Prompt 库 · FDE Copilot

> **本文的用途**：把本项目里**真正起作用的提示词模式**沉淀下来，供后续项目复用。
>
> **⚠️ 来源标注规则**（避免把提炼说成原文）：
> - `【逐字】`= 项目里逐字用过的原文；
> - `【骨架】`= 从项目里实际用过的文档中提炼的结构；
> - `【提炼】`= 从踩坑教训中总结出的模式，**项目中未逐字使用**。

---

## 一、本项目的 Prompt 有一个共同特征

**都要求「可被证伪的证据」，而不是「看起来对的说法」。**

这个项目的核心风险是：**AI 说「我做完了」，但实际没做**。所以所有关键 prompt 都在做同一件事——**要求输出可复算的坐标**：

| 要什么 | 不要什么 |
|---|---|
| `文件:行号` | 「相关文件里」 |
| 审计链 `seq` 号 | 「链上有记录」 |
| 测试退出码 + 脚本字节数 | 「测试通过了」 |
| `sha256` 前后对比 | 「没有改动」 |

## 二、A 类 · 核心功能开发（施工单）

### A1. 施工单骨架 `【骨架】`

**出处**：`Stage5-*施工单.md`（11 份）、`_inbox/NNNN-*-work-order.md`

```
# Stage <N> 第 <M> 批（<成本标注，如「单次重启、零配置改动」>）—— <一句话目标>

> Claude Code 于 <日期> <基于什么> 产出。
> **结论先行**：<先说结论>。但如果你<愿意付出什么成本>，请花在**这一件**上
> —— 它比 <备选项> 有价值得多，而且**不需要 <代价>**。

---

## 0. 为什么不补 <备选项>（附独立证据）

### <备选项 A>：**早已关闭**，不是"不可达"

<结论文档> §六（`:242-361`）记录 <日期> 活体两半均通过 ...（此处引用**具体证据**）

⇒ 你说的"<对方论断>"描述的是**今天的状态**，不是"<该判据>没验过"。
重跑一次只会验 <什么>，不会验**本批**。**不补。**

## 1. Context：为什么做、做完什么算成
## 2. 已拍板的决策（表格：决策 | 依据）
## 3. 🔴 本会话核实出的 SDK 事实（硬约束，拿不到）
## 4. 架构
## 5. 施工清单（表格：文件 | 职责）
## 6. 验证（表格：# | 判据 | 怎么验）
## 7. 本轮不做（但留好位置）
```

**为什么有效**（三个设计）：

| 设计 | 解决什么问题 |
|---|---|
| **结论先行 + 「为什么不补」** | 防止执行方**做完才发现方向错了**——先否定掉不该做的，再谈该做的 |
| **§3 「本会话核实出的 SDK 事实」** | 执行方**拿不到**这些事实（它没读过源码）。不写，它就会猜；猜就是缺陷 |
| **§7 「本轮不做」** | 明确划边界，防止执行方**顺手多做**导致回归面失控 |

---

### A2. 交付要求的三件套 `【提炼】`

```
完成后请附：
① 改动清单：每个文件 + 行号范围 + 改了什么
② 验证证据：**当场重跑**的命令 + 退出码 + 产物文件名
③ 未验/不确定的部分：明确列出，**不许用「应该没问题」代替**
```

> ⚠️ **为什么必须要求第③条**：AI 的默认行为是**报喜**。不明确要求「报忧」，它会用「应该没问题」把不确定的部分糊过去。

## 三、B 类 · Bug 调试与缺陷报告

### B1. 缺陷报告四段式 `【提炼】`

```
请按四段说清这个缺陷，**每一段都必须有源码依据**：

① **位置**：哪个文件、哪一行（给 `file:line`）
② **机制**：为什么会这样（要能指出具体哪个分支/哪行代码导致的）
③ **症状**：用户会看到什么现象
④ **谁发现**：是测试抓到的、还是人读出来的

⚠️ 如果你给不出①或②，就**不要下结论**——先说「我还没定位到」。
```

> ⚠️ **为什么要求「谁发现」**：同一个错误第 N 次被犯时，「是谁抓到的」决定了这是**纪律失效**还是**机制生效**——如果是变异测试同轮内抓到的，那说明防线在工作，不是纪律崩了。

---

### B2. 定位 bug 时先列状态空间 `【提炼】`

```
在你判断「这个实现在某情况下行为不对」之前，请**先把所有情况列成表**：

| 情况 | 期望行为 | 实际行为 | 是否一致 |

⚠️ 特别地：如果代码里有**嵌套三元**（`a ? X : b ? Y : Z`），
请把每个条件的取值**各写一行**，不要合并。
```

> **真实教训**：本项目曾判定某处实现「三个关键点都对」——**每点单独看都对**，但没有列组合，结果漏掉了「污染状态吞掉了红色告警」（`contaminated ? A : bad===0 ? B : C` 让 `bad>0` 被吞，显示「通过 7/8」却报 exit=3）。

---

### B3. 断言前先算一遍 `【提炼】`

```
凡是要写「比较 / 排序 / 计数」的断言，请：
① 先把**真实取值**代进去算一遍，或把证据**数一遍**；
② 两个数**对拍**后再写下来。

⚠️ 不许用「几乎」「大概」「绝大多数」糊过去。
```

> **真实教训**：本项目在这个模式上栽过多次，包括**在「认账/订正」时**又用了没算过的量——「认账」这个动作会让人松懈。

## 四、C 类 · 活体验证（驱动真实模型）

### C1. 活验驱动模板 `【逐字】`

**出处**：`_c2_live_drive.mjs`（真实使用并通过）

```
请只做一件事：直接调用 `<工具名>` 工具一次，参数 `reason` 填这个字符串（原样）：
<如实写的理由，例如：活验：验证 <什么> 的调用层接线（预期 <什么>，不改业务状态）>。
不要先读文件、不要先解释、不要调用任何其它工具，调用完就结束。
```

**四个设计要点**：

| 要点 | 为什么 |
|---|---|
| 「**只做一件事**」 | 模型有多做的倾向，多做的部分会污染判据 |
| 「**参数填这个字符串（原样）**」 | 防止模型自己发挥编一个理由 |
| 「**不要先读文件、不要先解释**」 | 防止它把回合消耗在探索上、或把结论预先「解释」成想要的 |
| **理由如实写** | ⚠️ **不许编业务理由**——见 C2 |

---

### C2. 🔴 不许编理由（最重要的一条）`【逐字 + 双向写法】`

```
`reason` 参数请填：
- 如果这次调用有**真实业务理由** ⇒ 就如实写那个理由；
- 如果**没有业务理由**（例如纯粹为了验证）⇒ 就写
  「活验：<验什么>（只读，不改业务状态）」。

⚠️ 不要为了「看起来像正常操作」而编一个业务理由。
```

> **为什么这条最重要**：这套系统的**全部价值**建立在「记录下来的话都是真的」之上。
> 一旦为了让测试通过而编造理由，**审计链就从「证据」退化成「表演」**。
>
> **真实教训**：本项目的某个施工单里曾写 `<如实写业务理由>` 作为占位符——这个占位符**预设了「一定有业务理由可写」**，等于在暗示执行方「编一个」。正确写法必须是**双向的**（如上）。

---

### C3. 活验前先问「最坏结果是什么」`【提炼】`

```
在决定「用这个动作来验证」之前，请算清：

| 如果一切正常 | 如果出错了 |
|---|---|
| 结果是什么？ | **最坏结果是什么？能不能撤销？** |

⚠️ 判据不是「我是不是在测试」，而是「**最坏结果是「被拒绝」还是「留下痕迹 / 推进了状态」**」。
```

> **真实教训**：本项目曾打算用「推进阶段」验证某个机制，当时的评估只算了「会不会被拦住」（不会），**没算**「最坏结果是业务状态被真实推进 + 链上永久留一条测试记录」。而那个动作**不是只读的**。

---

## 五、D 类 · 独立核证与防翻车

### D1. 让 AI 核 AI（抗自证）`【提炼】`

```
请不要相信任何人（包括你自己）在文档里写的结论。
请**从磁盘上的原始数据重新算一遍**，并回答：

① 你算出来的数是多少？
② 文档里写的是多少？
③ 如果不一致，是你错了还是文档错了？**列出判断依据**。

⚠️ 特别注意「全量属性」的问题：「链里有没有 X」必须**全量 parse**，
不能用 `tail` 或抽样的观感回答。
```

> **真实教训**：本项目曾凭 `tail -6` 断言「链里没有 allow 记录」，而**链的前部有 2 条**。尾部窗口对「全量属性」**零信息量**。

---

### D2. 用前先读接口 `【提炼】`

```
在调用任何现成的脚本/函数之前，请先：
① `grep '^export'` 看它导出了什么；
② 读 JSDoc 的 `@param` 确认参数形态；
③ 确认返回值是「直接数据」还是包了一层（如 `result.value`）。

⚠️ 不许凭印象调用。
```

> **真实教训**：本项目在核证时**三次凭印象调用**同一个断言脚本——把事件类型猜错、把未导出的函数拿来用、把参数形态搞错（传数组而非对象），**三次都返回 null**，而 null 被当成了「没问题」。

---

### D3. 报告里的标识符逐个当场核 `【提炼】`

```
在发出报告之前，请对**每一个**标识符做一次扫查：
工具名 / 文件名 / 路径 / 命令 —— **逐个当场核**，不许凭印象写。

⚠️ 特别是：行号核过了、工具名没核 —— **这类错误自己不会暴露**，
读者照错名字去找，会找不到，甚至**生出一份假的缺陷报告**。
```

> **真实教训**：本项目有一份回执，**数据、判据、链核对全对**，却把工具名写成了 `fde_run_validation`，**真名是 `fde-run-validation`**（连字符）。而同一份回执里引用的行号是当场 grep 来的、对的——**不是「整体不严谨」，是「对行号核了、对工具名没核」**。

## 六、E 类 · 交接与文档

### E1. 交接文档的「来路保留」写法 `【骨架】`

```
~~<原先的错误写法>~~
**订正（保留原判断的来路）**：本行原文写「<原话>」——**这句不成立**。
<说明为什么原判断是错的>
<给出正确答案 + 证据坐标>
```

> **为什么要保留「错误做法的来路」**：只给正确答案，读者**下次还会犯同样的错**（因为不知道当初为什么会那么想）。
> 加上「引原话 + 说明为何不能照抄 + 给替代量」，价值远高于只写正确做法。

---

### E2. 禁止「无条件断言」`【提炼】`

```
如果你想写「不需要 X」「永远不要 Y」「一定会 Z」「所有 A 都 B」，
请把**成立条件写在同一个句子里**。

⚠️ 无条件断言看起来完全正常，所以**比互相冲突更难发现**。
```

> **真实教训**：某施工单的标题写「不需要 seed」，而它依赖一个**从未写出的前提**（起点 = 6）。实际起点是 11，于是结论**当场反转成「必须 seed」**。

## 七、反模式：本项目验证过**无效**的 Prompt 写法

| ❌ 写法 | 为什么无效 |
|---|---|
| 「请确保代码正确」 | **不可证伪**。AI 会回「已确保」，你无从检验 |
| 「请仔细检查有没有 bug」 | 同上。且 AI 的「检查」通常只是**重读一遍自己的输出** |
| 「这个功能做完了吗？」 | 会得到「做完了」，但不含**证据** |
| 「请尽可能完善」 | 鼓励**范围蔓延**，破坏已稳定的部分 |
| 「**你确定吗？**」（无追问方向） | 只会得到「我确定」——这是**社交性确认**，不是核证 |
| 「按最佳实践实现」 | 「最佳实践」无定义 ⇒ AI 会按训练分布里最常见的方式做，而非**这个项目**需要的方式 |

**有效的替代**：

| ✅ 替代写法 |
|---|
| 「请给出**当场可复算的命令**，以及它的**退出码**」 |
| 「请**逐条**列出你检查了哪些点，每点给 `文件:行号`」 |
| 「请明确列出**没做完 / 没验证**的部分」 |
| 「请说明这个改动**可能破坏**哪些已有的东西」 |
| 「如果你给不出证据坐标，就直接说『我还没定位到』」 |

---

## 八、一句话总结

> **好 prompt = 把「我相信你」换成「请给我可以自己算一遍的东西」。**
>
> 本项目的所有 Prompt 都在服务这一个目标——因为在一个 AI 主导实现的项目里，
> **唯一能防住「AI 说自己做完了」的，是让它无法回避给出可复算的证据。**
