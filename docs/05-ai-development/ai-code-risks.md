# AI 代码风险说明 · FDE Copilot

> **本文写给**：要接手、审计或复用这套代码的人。
>
> **一句话结论**：这套代码**全部由 AI 生成**，且**AI 同时是它的验证者**。
> 这个风险**没有被消除**，只是被**压制**。本文说清压制手段，以及**哪些风险仍然敞着**。

---

## 一、最根本的一条风险：**自己验自己**

| 角色 | 承担者 |
|---|---|
| 写源码 | **AI** |
| 写测试 | **AI** |
| 跑测试 | **AI** |
| 判定「通过」 | **AI** |

**这在方法论上有固有缺陷**：
一个 AI 如果对某个机制有**错误理解**，它会**同时**把这个错误写进实现**和**测试里——
两边一致 ⇒ **测试全绿** ⇒ 错误被牢牢锁住。

> 🔴 **本项目的代码质量不能只用「41 套回归全绿」来论证。**
> 那 41 套**也是 AI 写的**。

---

## 二、实际观察到的 7 类风险（**每一类都有真实案例**）

> **口径**：下列分类来自《问题与 Bug 台账》收录的 **47 条**记录，
> 按「风险的形状」重新归类。**条数为该类别下的记录数**。

### 风险 1 🔴 **「仪器撒谎」——测试/脚本本身不报错，而是给出错误的绿灯**

| 案例 | 形状 |
|---|---|
| `0066-B`：`tests/_fde_d5_test.mjs` 是 **0 字节空文件** | 空程序 `node` 跑起来**零断言 + `EXIT=0`** ⇒ 产物写「PASS 9 / FAIL 0」 |
| `0026`：**自己的仪器对坏样本说 OK** | 检查器对合成坏样本**没判红** |
| `0055`：`tools/_replay_phase_audit.mjs` 遇坏 JSON **崩溃 + 零输出** <br>✅ **已修（2026-09-29）** | **它恰恰是「链坏时才跑」的那个** ⇒ 报警能力为零。（现状：`:45-47`/`:86`/`:99` 均 `catch` 兜底、`:135` 有 `exitCode`） |
| `0066-D`：**恒真判据** | `X == Y` 型断言**永远不可能红** |
| `0030`：`with` 方向把视窗 **fail-closed 丢了**（假绿） | 判据单向 ⇒ 漏了一半 |

> 🔴 **这是本项目最危险的一类风险**——因为它的输出**看起来完全正常**。
>
> **压制手段（已落地）**：
> ① `tests/_run_all_tests.sh` **对 < 400 字节的脚本预警**
> ② 固定动作：**每个检查器自带合成坏样本，不红就自己 `exit 1`**
> ③ 固定动作：写下 `X == Y` 判据后**立刻问「能不能构造出 `X ≠ Y` 的合法状态」**

---

### 风险 2 🔴 **凭印象写标识符 / 路径**

| 案例 | 形状 |
|---|---|
| `C32` 类 | 把工具名写成 `fde_run_validation`，**真名是 `fde-run-validation`**（连字符） |
| `C31` 类 | 凭印象写路径 `data/node_modules/…`，**实为** `dsh-home/profiles/web/node_modules/…` |
| `0023` | 认 `cfg.auditPath` 写错（**第 7 次同族失手**） |

> **为什么这一类特别危险**：**它自己不会暴露**。
> 读者照错名字去找，会**找不到**，甚至**生出一份假的缺陷报告**。
>
> ⚠️ **关键观察**：有一份回执**数据、判据、链核对全对**，**行号也是当场 grep 来的**，
> 却把**工具名**写错了 ⇒ **不是「整体不严谨」，是「对行号核了、对工具名没核」**。
>
> **压制手段（已落地）**：**发出前做一次「标识符扫」**——工具名 / 文件名 / 路径 / 命令**逐个当场核**。

---

### 风险 3 🟠 **判据错了，却看起来像「实现有缺陷」**

| 案例 | 形状 |
|---|---|
| 重放报「**3 处断链**」 | 按**文件行序**重放 ⇒ 应按 `seq` 排序 |
| 「**工具总数变多了**」 | 总数**本来就不是判据**（新工具注册会让总数上升） |
| `_deploy_diff` 报 `HAS-DIFF` | **README 也在对拍域内** |
| `0050` **逐名 diff 无区分力** | 10 次跳变 **8 次无链记录伴随**，且 diff 形状**逐字相同** |

> 🔴 **这一类最危险的地方是「下一步动作」**：
> 如果没人拦住，**下一步就是去「修」一个本来正确的实现**。
>
> **压制手段（已落地）**：**看到异常先怀疑自己的判据**；
> 先**全量 parse 打条数与位置**，再**独立算一遍期望**，与实现对拍。

---

### 风险 4 🟠 **「报喜」倾向——用「应该没问题」盖住不确定的部分**

**AI 的默认行为是汇报成功。**

| 表现形式 | 后果 |
|---|---|
| 「已确保代码正确」 | **不可证伪** |
| 「应该没问题」 | 不确定的部分**消失**了 |
| 只列做成的，不列没做的 | 接手者以为**都做完了** |

> **压制手段（已落地）**：**交付要求三件套**——
> ① 改动清单（文件 + 行号）② **当场重跑**的命令 + 退出码 ③ **明确列出没做完/没验证的部分**。

---

### 风险 5 🟠 **范围蔓延——顺手多做，破坏已稳定的部分**

| 案例 | 形状 |
|---|---|
| `0021` | **顺序失误**：先放行后拒绝，**多要一次停机** |
| `0010` | 认两处错，且**修法是 no-op**（改了等于没改） |

> **压制手段（已落地）**：施工单的 **§7「本轮不做」**——**明确划边界**。

---

### 风险 6 🟡 **验证方法本身也是错的（元层面）**

| 案例 | 形状 |
|---|---|
| `0027` | **自己的 shell 命令骗了我**（`$?` 取的是前一条命令的） |
| `0037` | **我给出的命令本身不成立** |
| `0052` | **仪器命令下错** |
| `0038` | **「所有」的域没写** |
| `0029` | 「按 `seq` 配对」错了；「4 次」**只有 3 条证据** |

> 🔴 **核心教训**：**仪器本身也是被测对象。**
> 写判据的人必须把自己的命令也当成「可能有 bug 的东西」来验。

### 风险 7 🟠 **多 AI 交接时的信息损耗**（**已通过组织变革消除**）

| 案例 | 形状 |
|---|---|
| `0037` | 搬运时**只搬论断句、丢掉限定它的邻句**（漏掉的是**反证**） |
| `0074` | **三处引用错误**（含同文档自相矛盾） |
| `0017` | **引用别人的行号，没写「相对哪一版」** ⇒ 读者照错坐标**生出假缺陷报告** |

> **压制手段（已落地）**：**2026-09-28 砍掉多 AI 交接**，改由单 AI 独立承担 ⇒ **这一整类风险消失**。

## 三、本项目**实际采用**的风险压制手段（6 条）

| # | 手段 | 针对哪类风险 |
|---|---|---|
| 1 | **判据必须落到磁盘事实**（哈希 / `seq` / 退出码 / 字节数） | 风险 1、4 |
| 2 | **核证方独立重算**，不看实现方的说明 | 风险 1、3、4 |
| 3 | **检查器自带合成坏样本，不红就 exit 1** | 风险 1 |
| 4 | **交付三件套**（改动清单 / 重跑命令+退出码 / 未验部分） | 风险 4、5 |
| 5 | **发文件前做标识符扫** | 风险 2 |
| 6 | **砍掉多 AI 交接** | 风险 7 |

## 四、🔴 **仍然敞着的风险（必须如实列出）**

| # | 风险 | 为什么压不住 | 建议 |
|---|---|---|---|
| **1** | **AI 自己验自己** | 结构性的。只要实现与验证是同一个模型，就**无法从根上消除** | 关键机制（`guard` / 哈希链 / 锁）**应由人类独立复核一遍** |
| **2** | **错误理解会同时写进实现和测试** | 两边一致 ⇒ 测试全绿 ⇒ 错误被锁住。**回归全绿不能证明语义正确** | 对**语义**做人工审查，不只看绿灯 |
| **3** | **没被记录的错误** | 本台账只有**被记录下来的 47 条**。没写进文档的**不在这里** | 不能把这份台账当作「全部缺陷」 |
| **4** | **测试覆盖 ≠ 场景覆盖** | `0082` 记录过「**46 断言未覆盖**」的缺陷 | 定期做**变异测试**（本项目已用过，见 M1/M2/M12/M23） |
| **5** | **模型版本漂移** | 项目**没记录**各阶段用的模型版本 | 若代码要长期维护，**固定模型版本** |
| **6** | **无版本控制** | 7 天 35 次改动**无法逐行追溯** | **立刻 git 化**（《后续迭代规划》P0-1） |

## 五、给审计者的检查清单（**建议按这个顺序验一遍**）

```
□ 1. git 化了没有？能不能逐行追溯？
□ 2. 41 套回归，每一套都【真的跑过】吗？
      → 查脚本字节数（ls -la，别用 wc -l）+ 当场重跑 + 取退出码
□ 3. 有没有恒真判据？（写下 X==Y 后能构造出 X≠Y 的合法状态吗）
□ 4. 每个检查器都对自己的坏样本判红吗？
□ 5. D2 的 hash 是【真的重算】还是只验格式？
      → 这是 0014 记录过的真缺陷，务必实测
□ 6. 三条审计链的 schema 差异，排查脚本都兼容了吗？
□ 7. 锁的强夺条件是【双条件】吗？（超时 && 持有进程已死）
□ 8. 报「断链」时，是【按 seq 重放】还是按文件行序？
□ 9. `_deploy_diff` 的对拍域包含 README 吗？
□ 10. 那些「🔴 待办」的记录，是真待办还是【已解除但没改】的 stale red？
```

## 六、一句话总结

>
> 它的**可信度不来自「AI 说它对」**，而来自——
> **每一条结论都指着一个可以被你独立复算的磁盘事实**。

> **请你不要相信本文的任何结论，去磁盘上自己算一遍。**
