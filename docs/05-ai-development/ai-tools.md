| 项 | 内容 |
|---|---|

| **模型** | ⚠️ **未在项目中记录** |
| **使用时段** | 2026-09-22 — 2026-09-28 |
| **提及次数** | **184 次**（全量统计中最高） |
| **产出** | `.workbuddy/memory/` 下 4 份日期工作日志、`_wb_*.ps1`（8 个窗口自动化脚本）、`_wb_*.png`（6 张界面截图） |

> 📌 **另有一批「探它」的脚本，2026-09-29 已删除**：`_wb_api.mjs`、`_wb_gateway.mjs`、`_wb_probe.mjs`、`_wb_tail.mjs`（共 4 个）。
> 注意归属 —— 它们**不是 WorkBuddy 的产出**，而是 **Claude Code 写的只读探针**（探 WorkBuddy 的本机 IPC / HTTP 网关、读它的会话记录），
> 用来在"两个 AI 交接"那段时期核对方到底做了什么。WorkBuddy 退出后它们再无用途，连同 README 里的说明行一并移除。
> 决策依据与留档（字节数 / SHA-256）见 [CHANGELOG](../../CHANGELOG.md) 的「清理 WorkBuddy 遗留脚本」。

**承担的工作**：早期批次（Stage 3/4/5 的多个补丁）的实现与回执。

**为什么退出**：用户判断「两个 AI 互相交接」的**沟通成本高于收益**——每一轮都要写施工单、等回执、核对，而纠正内容多是措辞与计数，极少改变结论。

> **这是一个值得记录的经验**：多 AI 协作的瓶颈不在模型能力，而在**交接界面的信息损耗**。

## 三、协作模式的三阶段演变

```
阶段一（09-22 — 09-27）：双 AI 并行
┌──────────────┐  施工单   ┌──────────────┐
│  Claude Code │ ────────► │  WorkBuddy   │
│  （出计划）   │ ◄──────── │  （写源码）   │
└──────────────┘   回执    └──────────────┘
         │                        │
         └──── 活验 ←─────────────┘
               （Claude Code 负责）

阶段二（09-27 前后）：三 AI 短暂交替
        加入 Trae 接力第三批

阶段三（09-28 之后）：单 AI 独立
┌──────────────────────────────┐
│  Claude Code                 │
│  写源码 + 写测试 + 活验 + 文档 │
│  （不再产出施工单、不等中转）  │
└──────────────────────────────┘
```

**为什么最终收敛到单 AI**：

| 双 AI 并行的问题 | 单 AI 的改善 |
|---|---|
| 每轮要写施工单 + 等回执 | 直接做 |
| 交接文档里的编号/行号会漂移 | **不存在交接** |
| 一方引用另一方文档时断章取义 | 同一上下文，无转述 |
| 纠正的内容多是措辞/计数，极少改变结论 | 省掉整轮往返 |

## 四、AI 在项目中承担的**具体**角色（可核查）

| 角色 | 具体动作 | 可核查痕迹 |
|---|---|---|
| **实现者** | 写 4 个插件的 `lib/*.js` | 源码文件 + `_snapshots/` 的 35 份改动前快照 |
| **测试者** | 写 41 套离线回归 | `_*_test.mjs` + 各自的 `_*_out.txt` |
| **验证者** | 在真进程内验证 | `_*_live*.mjs` + 审计链记录 |
| **独立核证者** | 写脚本核验自己的结论 | `_cc_*` 系列（约 20 个） |
| **自我纠错者** | 发现并修复自己的缺陷 | 见《AI 代码风险说明》 |
| **文档者** | 写 README、回执、本套文档 | 190 个 `.md` |

> ⚠️ **一个诚实的说明**：AI **既是实现者，也是验证者**——这在方法论上有固有风险（自己验自己）。本项目的应对办法是：**验证必须落到磁盘上可复算的证据**（审计链 `seq`、文件哈希、退出码），而不是「AI 说它对」。详见《AI 代码风险说明》。
