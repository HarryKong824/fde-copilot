## 1. 项目背景与解决的痛点

### 1.1 业务背景：FDE 是什么

**FDE（Forward Deployed Engineer，前置交付工程师）** 是驻场在客户现场、把通用 AI 平台能力落地成客户可用方案的工程角色。其工作特征：

- **要改客户的业务语义**，而不是只写代码——典型产物是本体（ontology，即「业务对象 + 规则」的形式化描述）；
- **要按阶段推进**，从初次接触到最终交付，每个阶段有不同的准入条件；
- **每一个动作都可能不可逆**——改错一条业务规则，客户的核心流程就可能出错。

### 1.2 痛点（这套插件要解决的四个问题）

| # | 痛点 | 后果 |
|---|---|---|
| 1 | **改本体没有护栏** | 任何人都能改业务规则，没有门禁、没有留痕，出错后无法回溯是谁在什么时候改的 |
| 2 | **规则本身不可信** | 写了「禁止某操作」的规则，但规则引用的属性还没定稿、或者规则根本编译不过，**却照样生效** |
| 3 | **阶段推进没有硬约束** | 「还没做完就宣布进入下一阶段」——跳过校验环节，等于跳过门禁 |
| 4 | **审计数据只在本地** | 出事后要追责，发现日志只在一台机器上，且可以被静默篡改 |

**这四个痛点分别对应本项目的四层护栏**：改本体的入口管控（门禁）、规则可信度校验（D1/D3）、业务阶段状态机（Phase）、审计外置与交叉校验（L1–L4）。

### 1.3 本项目的定位

**不是**做一个聊天机器人，**而是**给 AI 助手戴上「工程安全装置」：

> 让 AI 在客户现场能干活，同时**每一个危险动作都被拦住、被记录、可追溯**。

## 2. 目标用户

### 2.1 主要用户：FDE（前置交付工程师）

在自己或客户的 DSH 环境里，用 AI 助手推进交付。**他们关心的是**「我这一步做了，能不能撤回？出问题谁负责？」，而不是「AI 有多聪明」。

### 2.2 次要用户

| 角色 | 关注点 | 对应文档 |
|---|---|---|
| **交付团队负责人** | 阶段推进是否合规、门禁是否真的拦住过 | 审计链、`fde_phase_advance` 回执 |
| **安全 / 合规审计员** | 谁能改规则、改了什么、能不能事后复核 | 审计链 L1–L4、break-glass 记录 |
| **后续开发者** | 这套插件的边界在哪、怎么改不破坏验证 | 各插件 `README.md`、`docs/02-development/` |

### 2.3 明确**不是**给谁用的

- ❌ **终端消费者**——没有图形界面，所有交互通过 DSH 里的 AI 助手进行；
- ❌ **想开箱即用的团队**——本项目是 **PoC 阶段**（0.0.1），部署需要手工装配，且已明确记录若干能力降级（见《功能清单对照表》）。

## 3. 核心价值

| 价值 | 具体体现（已落地） |
|---|---|
| **危险动作拦得住** | 改本体、推阶段两个入口都钉了守卫（`guard`），**运行时不通过就只能被拒绝**——不是靠提示词提醒 AI 自觉 |
| **拒绝必须留痕** | 每一次拒绝都写进哈希链审计（`decision: "deny"` / `"lock-contended"`），带原因与序号 |
| **结论绑定内容** | 校验结论用**文件内容哈希**锚定。改了被校验的文件，旧结论**自动失效**——不存在「用过期结论蒙混过关」 |
| **审计链不可静默篡改** | 每条记录链式哈希（`sha256(prevHash + record)`），重放可验；链一断立刻能发现 |
| **故障时保守失败** | 全部按 **fail-closed** 设计：判定不了「安全」时一律判「不放行」，而不是放行 |

## 5. 技术栈选型

### 5.1 运行时与语言

| 项 | 选型 | 说明 |
|---|---|---|
| 运行时 | **Node.js**（ESM，`type: "module"`） | 与 DSH 宿主同构，插件直接跑在宿主进程内 |
| 语言 | **纯 JavaScript**（无 TypeScript 编译步骤） | PoC 期减少构建链；类型靠 JSDoc 注释表达 |
| 包管理 | npm（`peerDependencies` 声明宿主 SDK） | 插件**不打包**宿主 SDK，由宿主提供 |

### 5.2 宿主平台

**DeepSeek Harness（DSH）**——插件的运行载体。本项目用到的宿主能力：

| 宿主能力 | 用途 |
|---|---|
| `ctx.tools.guard` | **同步、单调、只能否决**的守卫——本项目所有门禁的挂载点 |
| `ctx.tools.restrict` | 工具面过滤（受保护阶段隐藏危险工具） |
| `ctx.emit` / `ctx.on` | 跨插件通信（校验结论从 dsl 传到 phase） |
| `defineTool` | 工具注册（宿主自有 DSL 描述参数与输出） |
| `ctx.approval` | 人工确认请求（D4/D5-pre 的「询问」） |

### 5.3 关键依赖

**运行时第三方依赖：零个。**

| 依赖 | 类型 | 用途 |
|---|---|---|
| `@deepseek-ai/dsh-tools@0.1.2-rc.1` | peer | 工具注册与守卫 API |
| `@deepseek-ai/schemastery@3.18.2` | peer | 配置项 schema（仅供配置面板提示） |

> **为什么零运行时依赖是刻意的**：插件跑在客户现场的宿主进程里，每多一个第三方包就多一份供应链风险与一次版本冲突的可能。**YAML 解析、哈希链、状态机全部自己实现**（如 `yamlsubset.js` 只支持用到的 YAML 子集），代价是功能受限，收益是**行为完全可预测**。

### 5.4 关键选型：**为什么不用数据库**

状态与审计的存储选型，是本项目最容易被误解的一处：

| 数据 | 存储形态 | 为什么不用数据库 |
|---|---|---|
| 业务阶段状态 | `<projectRoot>/memory/state.yaml` | 需要**人可读、可手工修复**——出事故时运维要能直接打开看、手工改 |
| 审计链 | `*.jsonl`（每行一条 JSON） | 只需要**追加**，不需要查询；追加写 + 链式哈希即可满足防篡改；文件可直接用 `grep` 排查 |
| 本体规则 | `*.yaml`（4 个受控文件） | 客户要能审阅、能进版本控制；YAML 比数据库表更贴近「业务规则」的原始表达 |
| 会话追溯 | DSH 宿主的 `session.jsonl`（多帧 zstd 压缩） | 宿主已有能力，不重复造 |

**代价（如实说明）**：没有事务、没有并发控制的原生支持——所以本项目**自己实现了单写者锁**（`<projectRoot>/memory/.state.lock`，含 PID 存活检测与超时强夺）。

### 5.5 未采用的方案（及原因）

| 方案 | 为什么没选 |
|---|---|
| 用宿主 `workflow.phase` / `goal.phase` 表达业务阶段 | 这两者是**进度叙述**，监听器返回值被丢弃、事件提交后才发出，**拦不住**任何东西 |
| 自定义 SessionEvent 类型持久化状态 | spec 第八节**明确禁止**：未知事件类型在恢复时 fail-closed，会导致会话拒绝恢复 |
| 用第三方 YAML / JSON-Schema 库 | 见 §5.3——供应链风险与行为不可预测 |
| 动态 `import()` 加载护栏实现 | 等于开出**代码执行面**（见《AI 代码风险说明》中的已知降级项） |

## 9. 术语表（阅读本套文档前建议先看）

| 术语 | 含义 |
|---|---|
| **FDE** | Forward Deployed Engineer，前置交付工程师 |
| **Ontology（本体）** | 业务对象 + 规则的形式化描述。本项目里是 4 个受控 YAML：`objects.yaml`（对象与属性）、`logic.yaml`（规则）、`actions.yaml`（动作）、`guards.yaml`（护栏实现） |
| **DSH** | DeepSeek Harness，本项目的宿主平台 |
| **插件（plugin）** | 跑在 DSH 进程内的功能单元，通过 `apply(ctx)` 装配 |
| **guard（守卫）** | 宿主提供的同步否决钩子——**拦得住**的机制，与「提示词提醒」本质不同 |
| **gate / dsl / phase / memory** | 本项目四个插件的简称 |
| **D1 / D2 / D3 / D4 / D5** | 五类门禁校验：D1 护栏绑定、D2 审计链、D3 规则反例、D4 客户验收（ask）、D5 合规 |
| **deny / ask** | 两种门禁语义：`deny` 直接拒绝；`ask` 走人工确认 |
| **fail-closed** | 判定不了就**不放行**（与之相对的是 fail-open：判定不了就放行）。本项目一律 fail-closed |
| **影子模式（shadow）** | 只记录「本该拒绝」而不真的拒绝，用于上线前观测误拦率 |
| **break-glass（逃生门）** | 紧急情况下的人工放行通道，独立留痕、事后可审计 |
| **哈希链 / 审计链** | 每条记录含前一条的哈希，形成链；任何一条被改都会导致后续全部哈希不符 |
| **活验（活体验证）** | 在**真实运行进程内**验证，与「离线单元测试」相对 |
| **锚定（anchor）** | 把校验结论与被校验文件的**内容哈希**绑定，文件一改结论即失效 |
