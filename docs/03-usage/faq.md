# 常见问题 FAQ · FDE Copilot

> **说明**：下列问题**全部来自本项目的实际发生**——包括开发期踩过的坑、活验中发现的缺陷、以及使用者最可能困惑的点。凡是「我们踩过」的，都写了当时的症状与真正的根因。

---

## A. 使用类（普通用户）

### A1. AI 说「操作被拒绝了」，是坏了吗？

**不是。** 被拒绝是**设计行为**。

这套系统的原则是 **fail-closed**：判定不了「安全」时，一律判「不放行」，而不是放行。所以它会**宁可拦住正确的操作，也不放过错误的操作**。

**你该做的**：
1. 读拒绝理由——里面通常已经写了「怎么补」；
2. 按提示补齐；
3. 如果你确信是**护栏错了**（不是你的操作错了），走逃生门（见《用户操作手册》§5.5），**并把这个问题报出来**。

---

### A2. 为什么不能从阶段 3 直接跳到阶段 5？

因为**跳过阶段 4 等于跳过门禁**。

阶段之间是 `current → next(+1)` 的硬约束。阶段 4 挂着 D2（审计链校验）和 D3（规则可信度校验）两道门禁——允许跳跃，这两道门禁就形同虚设。

**要做的事**：按顺序推进，把阶段 4 的门禁过掉。

---

### A3. 我改了一条规则，为什么之前跑过的校验结果不算数了？

**这是设计，不是 bug。**

校验结论用**文件内容哈希**锚定。你改了文件 ⇒ 哈希变了 ⇒ 旧结论**自动失效**。

**为什么必须这样**：否则会出现「改了规则，但拿改动之前通过的结论来蒙混过关」的漏洞。这正是这套系统要防的事情之一。

**你该做的**：重新跑一次校验。

---

### A4. 写规则时报解析错误，明明 YAML 语法是对的？

**大概率是引号问题。**

本项目的 YAML 解析器是**自研的受限子集**，对**行内集合直接调 `JSON.parse`**，所以 `{}` / `[]` 内部**必须写合法 JSON（双引号）**：

```yaml
# ✅ 正确
condition: {">": [{"var": "treatment.dose_mg"}, 100]}

# ❌ 错误：单引号解析失败
condition: {'>': [{'var': 'treatment.dose_mg'}, 100]}
```

---

### A5. 我明明没写 `maturity`，为什么规则被判失败了？

因为**不写就是 `draft`（未定稿）**，这是**故意的保守设计**。

规则：
- 属性不写 `maturity` ⇒ 默认 `draft`；
- **`deny` 类规则引用 `draft` 属性 ⇒ D3 判失败**（报 `DraftReference`）。

**为什么**：一条「禁止某行为」的规则，如果引用了一个还没定稿的属性，等于**用不确定的东西去禁止确定的事**——这种规则不该生效。

**怎么修**：要么把属性定稿（`maturity: verified`），要么别在 `deny` 规则里用它。

---

### A6. 「逃生门」（break-glass）是不是后门？可以随便用吗？

**不是后门，也不该随便用。**

| | 普通操作 | 逃生门 |
|---|---|---|
| 留痕 | 有 | **有，且独立留痕** |
| 后续要求 | — | **7 天补正期**——7 天内必须回头把问题修掉 |
| 分类 | — | 必须声明是 `deny_defect`（护栏错） / `scope_edge`（边缘场景） / `evasion`（确实在绕过） |

**什么时候该用**：护栏**错了**，却把正确操作拦住了，而你**等不起**。

**什么时候不该用**：只是嫌麻烦。

---

### A7. 确认弹窗（D4/D5-pre）我点了「拒绝」，会怎样？

**整个推进会被取消。** 系统不会「忽略拒绝继续走」。

而且拒绝**也会被记账**——`phase.jsonl` 里会留下一条记录（实测本项目链上有 `phase-advance-d4-ask:confirmed` 与 `:rejected` **各一条**，都是真实发生的）。

> ⚠️ **不要为了「测试一下」而点确认**。确认会被记账且不可撤销。

---

### A8. 怎么知道 AI 到底做了什么？

三种方式：

1. **直接问**：「查一下最近的审计记录」；
2. **看链**：`<DSH_HOME>\fde-audit\phase.jsonl`（每行一条 JSON）；
3. **筛选**：`grep '"decision":"deny"' phase.jsonl` 看所有被拒的操作。

## B. 运维类（技术人员）

### B1. 🔴 重放审计链报「3 处断链」，但系统明明没被改过？

**这是本项目最著名的一个假警报。根因是「按文件行序重放」。**

| 重放方式 | 结果 |
|---|---|
| 按**文件行序** | ❌ 报 **3 处假断链** |
| 按 **`seq` 升序** | ✅ **断链 0、哈希不符 0** |

**为什么**：同一毫秒的两个并发写者（如 `memory-confirm` 与 `session-event`）会分到**相邻 `seq`**，而**落盘次序可能被 OS 打乱**。实测出现过第 224 行 `seq=223` 排在第 223 行 `seq=224` **之后**。

> ⚠️ **教训**：当时第一反应是去查「实现是不是有缺陷」——差一点就去改一个**本来正确**的实现。**先全量 parse 打条数与位置，再独立算期望与实现对拍**，别急着改代码。

> ⚠️ **按 `seq` 重放还有新失效面**：必须**同时**断言 `seq` **无重号、无缺号**，否则重放会静默跳过一条而不报断链。

**正确命令**：
```bash
node tools/_replay_phase_audit.mjs    # 期望：断链 0 处 / CHAIN-INTACT
```

### B2. 哈希重算总是不符，公式是抄的没错啊？

**检查你是不是手工拼装了字段。**

```js
// ✅ 必须用 rest 解构——它保留 record 其余键的【原顺序】
const { prevHash, hash, ...record } = row
linkHash(prevHash, record) === hash

// ❌ 手工挑字段重建对象（键顺序变了，JSON.stringify 结果就变了）
linkHash(row.prevHash, { seq: row.seq, type: row.type, ... })
```

`JSON.stringify(record)` **依赖键顺序**。重算哈希必须与落盘时的键顺序**完全一致**。

### B3. `tests/_deploy_diff.mjs` 报 `HAS-DIFF`，但我只改了 README？

**那正是原因——`README.md` 也在对拍域内。**

本项目真实踩过：只改了源 README 没同步副本 ⇒ 报 `HAS-DIFF`，而 14 个文件里**只有这一处**不一致 ⇒ 极易被误读成「代码没同步」。

**修法**：补一次 `cp` 即可。**README 不参与运行时，不必重启。**

---

### B4. 为什么「受保护阶段隐藏了工具」之后，工具**总数反而变多了**？

**因为总数不是判据——要看逐名 diff。**

本项目实测：新工具注册会让 header 里的工具总数**不降反升**（36→37），而 `pwsh` **确实被摘掉了**。

> ⚠️ **验收 restrict 必须逐名 diff，不能看总数。**

另注：header **只在清单变化时追加**，所以「header 条数」也不能当作「检查次数」。

---

### B5. 让 AI 续会话发第二条指令，它却说「没有工具调用」，明明调了？

**这是驱动脚本的缺陷（已修复），不是 AI 的问题。**

**症状**：`--sid` 续会话时报「工具事件 0 条」+ 回显**上一轮**的文本。

**根因**：`waitSettle` **不设回合基线**——续会话时**旧回合的 `finish` chunk 仍在记录里**，循环**第一次轮询**就命中它并返回，**新回合被整个丢掉**。

> ⚠️ **这个缺陷最危险的地方是它的形状**：症状与「模型真的没调工具」**完全一样**。仅凭输出无法区分。

**修法**：发问前先取 `maxTurn` 基线，只认**新**事件。

---

### B6. 某个测试套件「全绿」，但我怀疑它根本没跑？

**查两件事**：

```bash
# ① 脚本字节数（⚠️ 别用 wc -l：无换行符的文件也报 0）
ls -la tests/_fde_d5_test.mjs

# ② 看它自己的产物文件
```

**真实教训**：`tests/_fde_d5_test.mjs` 曾是 **0 字节**，而跑一个空程序 `node` 必然 **零断言 + EXIT=0** ⇒ 产物文件里写着「PASS 9 / FAIL 0」，**却从未真跑过**。

> ⚠️ **结果文件不能自证「测试跑过」**。「跑过」要三件套：**脚本字节数** + **当场重跑** + **退出码**。
>
> ⚠️ `tests/_run_all_tests.sh` 已内置防护：脚本 **< 400 字节即预警**。

### B7. 🔴 拒绝理由是「锁未过期」，但那个进程早就死了？

**注意锁的强夺条件是「双条件」，不是单条件。**

```js
stale = timedOut && holderDead     // 超时必须【且】持有 PID 已死
```

三种情况的正确行为：

| 情况 | 行为 |
|---|---|
| 锁未过期 | 拒绝 |
| 已超时 **+ 持有 PID 活** | **拒绝**（不抢活进程的锁——它可能在做长任务） |
| 已超时 **+ 持有 PID 死** | 强夺 + 审计记 `lock-steal` |

**所以你看到「超时了却不释放」是正常的**。先确认那个 PID 是否真的还活着：

```bash
tasklist | grep <PID>
```

> ⚠️ 另外注意：`acquireLock` 有**两个不同的拒绝文案**（「锁未过期」/「已超时但持有进程仍存活」）。如果你在写判据，**别只匹配其中一种措辞**——这是本项目自己踩过的坑（判据写窄 ⇒ 假红）。

### B8. 三份审计链，为什么有的记录没有 `type` 字段？

**因为三份链的 schema 本来就不同。**

| 链 | 类型字段 |
|---|---|
| gate | `type`（部分）／ `tool`+`decision`（守卫记录）／ `event`（链轮转） |
| phase | `type`（部分）／ `tool`+`decision`（守卫记录） |
| memory | **`kind`**（+ `eventType`、`sessionSeq`、`data`） |

**排查时最省事的写法**：

```js
const k = x.type ?? x.kind ?? '(无类型字段)'
```

> ⚠️ **这是一处真实的技术债**，已记在《技术架构说明》§9。

### B9. 「D1」到底指什么？文档里看到两个意思？

**确实有两个 D1，同名不同物**——这是本项目最容易混淆的一处：

| 缩写 | 出处 | 含义 |
|---|---|---|
| **D1（护栏绑定）** | spec §3 | 检查「动作的护栏有没有绑到可执行实现、测试过没过」 |
| **D1（审计外置）** | spec §8 | 审计的四层：L1 本地采集 / L2 outbox / L3 TelemetryBackend / L4 交叉校验 |

> ⚠️ **读文档时务必看它标的是 §3 还是 §8。**

---

### B10. 我的审计链记录比文档里写的条数多/少，正常吗？

**正常——链是持续增长的。**

文档里引用的条数是**某个时间点的实测值**（带日期）。例如「phase 链 119 条」是 2026-09-29 的实测。

**要复核当时的数量**，看文档里是否写了 `seq` 号——本项目所有引用都尽量带 `seq`（如「活验 `phase.jsonl:107`」），那是**不随时间漂移的坐标**。

---

### B11. 部署后 AI 说某些工具「不存在」，但目录明明在？

**两个可能**：

1. **没重启 DSH** —— 改了 `lib/*.js` 必须重启才生效；
2. **当前阶段隐藏了它** —— 受保护阶段（`protectedPhases: ['4','6','10']`）会隐藏 `denyTools` 名单里的工具。

**确认方法**：让 AI 列出当前可用工具，看是否含目标工具。**不要用「工具总数」判断**（见 B4）。

---

### B12. 改了配置文件的模式（shadow ↔ enforce），要重启吗？

**不需要。**

改 `lib/*.js` **需要**重启；切 `mode` **不需要**——本项目实测过这一点。

## C. 概念类

### C1. 这套东西和「提示词里让 AI 注意安全」有什么区别？

**本质区别：拦不拦得住。**

| 方式 | 能拦住吗 |
|---|---|
| 提示词提醒 AI | ❌ AI 可以不听 |
| **守卫（guard）** | ✅ **同步、单调、只能否决**——返回拒绝后无人能翻盘 |

这套系统挂在宿主的 `tools.guard` 上，是**机制**，不是**建议**。

---

### C2. 为什么「审计链」要用哈希链，不用普通日志？

因为**普通日志可以被静默篡改**——改掉一行，没有任何痕迹。

哈希链每条记录含前一条的哈希，**改任何一条都会导致后续全部哈希不符**。这是「事后追溯」能成立的前提。

---

### C3. 「fail-closed」和「fail-open」的区别，为什么选前者？

| | 判定不了时 | 后果 |
|---|---|---|
| fail-open | **放行** | 故障时静默变成「无保护」 |
| **fail-closed**（本项目） | **不放行** | 故障时变成「过于严格」，但**不会漏保护** |

**代价**：可能出现「明明该放行却被拦住」。**收益**：不会出现「明明该拦住却放行了」。

对一套**门禁**系统来说，前者是可接受的麻烦，后者是**无法接受的漏洞**。

---

### C4. 为什么没有数据库？数据会不会不可靠？

**没有数据库是刻意选择**，不是偷懒：

| 数据 | 存储 | 为什么 |
|---|---|---|
| 状态 | YAML | 出事故时运维要能**直接打开看、手工修** |
| 审计 | JSONL | 只需要**追加**，链式哈希即可防篡改，`grep` 就能排查 |
| 本体 | YAML | 客户要能审阅、能进版本控制 |

**代价（如实说明）**：没有事务、没有原生并发控制 ⇒ 本项目**自己实现了单写者锁**。

---

### C5. 这套系统能多租户 / 多人同时用吗？

**不能**——这是 **PoC 阶段（0.0.1）** 的明确边界：

- 没有账号系统；
- 设计场景是**单机单用户**；
- 并发控制只做到「单写者锁」这一层（防止同时写坏一个文件）。

多租户、多用户协作**不在当前实现范围内**。
