## 二、逐条记录

### CR-01 🔴 多 AI 协作 → 单 AI 独立

| 项 | 内容 |
|---|---|
| **原方案** | Claude Code 出施工单 → WorkBuddy 写源码 → Claude Code 活验（双 AI 并行，Trae 阶段性接力） |
| **改为** | **Claude Code 独立承担全部**：写源码 + 写测试 + 活验 + 文档 |
| **日期** | 2026-09-28 |
| **决策方** | **用户拍板**（原话：「从现在起不需要 WorkBuddy 参与了，你自己完成」） |

**变更理由（实测数据）**：

| 问题 | 证据 |
|---|---|
| 每轮要写施工单 + 等回执 | 123 份 `_inbox/` 文档，其中大量是往返本身 |
| 交接文档里的**行号/编号会漂移** | `0074`：三处引用错误（含同文档自相矛盾） |
| 一方引用另一方文档时**断章取义** | `0037`：第 19 次，搬运时只搬论断句、丢掉限定它的邻句 |
| **纠正的内容多是措辞/计数，极少改变结论** | 核证发现的 47 条中，🟡 C 级（记账/表述）占 **17 条** |

**影响**：`0093`（E1 break-glass）成为**第一份没有往返的批次**——从这天起实现与核证由同一 AI 承担。

**残留风险（如实记录）**：AI 同时是**实现者**和**验证者**。本项目**不能声称已消除这个风险**，只能用「判据必须落到磁盘事实」来压制。见《AI 代码风险说明》。

### CR-02 D4 从 `deny` 降为 `ask`

| 项 | 内容 |
|---|---|
| **原方案** | D4（客户验收确认）是 `deny` 类门禁——**未确认则直接拒绝** |
| **改为** | D4 走 **`approval.ask`**——向用户**提问**，由用户答复决定 |
| **日期** | 2026-09-28（`_inbox/0089`） |

**理由**：D4 问的是「**客户是否已验收**」——这是一个**只有人知道答案**的问题。
用 `deny`（机器判定）去处理一个**人类业务事实**，会让门禁变成「猜」。

**新语义**：

| 用户答复 | 结果 |
|---|---|
| 确认 | 继续推进，链上记 `phase-advance-d4-ask:confirmed` |
| **拒绝** | **整个推进被取消**，链上记 `:rejected` |

> ⚠️ 本项目实测链上 **`:confirmed` 与 `:rejected` 各有一条**——都是真实发生的，不是测试。

### CR-11 `from` 字段语义修正

| 项 | 内容 |
|---|---|
| **原设计** | `from` 字段**链式**指向（指向上一条记录） |
| **改为** | `from` **恒指「最后一条 applied」** |

**理由**（`0005`）：restrict 审计链的 `restored` / `replaced` 事件需要**能回溯到「恢复到哪个状态」**。
链式指向会让这个回溯变成「走一条链」，而实际需要的是「**一步到位知道恢复的目标**」。

**配套**：落 `restored` 事件 + `from` 改指 `applied`。

### CR-15 🔴 判据变更：逐名 diff 降为辅助

| 项 | 内容 |
|---|---|
| **原判据** | 工具面**逐名 diff**（看 header 里少了哪些工具） |
| **改为** | **主判据 = 链事件 + 时间紧邻配对（±秒级）**；逐名 diff **降为辅助** |
| **驱动** | **实测证伪**（`_inbox/0050`），不是主观判断 |

**证伪数据**：

| 观测 | 结果 |
|---|---|
| 16 条 header 里 `pwsh` 跳变 | **10 次** |
| 其中**无链记录伴随** | **8 次** |
| 10 次的 diff 形状 | **逐字相同**（`移除["pwsh"]` / `新增["pwsh"]`） ⇒ **无区分力** |
| 实测唯一强配对 | `#25 lifted` **前 1.53 s 无、后 28 ms 有** |

> **这条变更的意义**：**判据本身也是要被验证的对象**。
> 一个错的判据不会报错——它只会给你**一个看起来很正常的答案**。

## 四、三条最值得复用的变更管理经验

### 4.1 ✅ 每条变更都记了「**决策方**」和「**理由**」

**为什么**：区分「**用户拍板**」和「**实测驱动**」极其重要。
- 前者不能改（是需求）；
- 后者可以改（是结论，新证据来了就该翻）。

CR-15 就是典型的「实测驱动」——它的依据是**证伪数据**，不是偏好。

---

### 4.2 ✅ 降级必须**显式标注**，且**不许被说成「已实现」**

CR-04（D1 的 `impl` 用 DSL 而非真函数）是本项目**唯一一条与 spec 不一致的降级**。
它的处置方式值得记住：

| 做了什么 |
|---|
| 在《功能对照表》§5 **单列 PoC 降级** |
| 写进插件 `README.md` 的**诚实缺口清单** |
| 明确写明「**不得在任何交付文案里被说成『已按 spec 实现』**」 |

> **为什么这条重要**：降级本身不可怕，**被忘掉的降级**才可怕——
> 它会让后来的人以为「这条已经有人做过了」。

---

### 4.3 ✅ 变更要写「**副作用 / 影响面**」

CR-13（YAML 锚点消重）的副作用——「改锚点会同时影响多个插件」——被**单独写出来**并进了运维手册。

**为什么**：变更的**代价**往往不在变更本身，而在**它碰到的东西**。
