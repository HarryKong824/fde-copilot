## 〇、读这份日志前需要知道的三个词

| 词 | 在本项目里的含义 |
|---|---|
| **Stage** | 一次大的功能推进（如 Stage 5 = phase 状态机；Stage 5.5 = D2/D3 接线；Stage 5.6 = D5 合规门禁） |
| **批（batch）** | Stage 内部的一次交付-核证往返。**一个批 = 一份施工单 + 一份回执 + 一次核证** |
| **施工单 / 回执** | 施工单 = 交给实现方的任务书；回执 = 实现方交回来的完成说明。**两者都在 `_inbox/`** |

> 🔴 **本项目最关键的一个特征**：**每一批都有核证环节**，核证方会去磁盘上**重新算一遍**。
> 因此这份日志里会大量出现「**认错**」「**撤回**」「**证伪**」——**那不是项目失控的证据，恰恰是质量控制机制在工作的证据**。

## 三、三条贯穿全周期的工程约束（**每个批次都要面对**）

| # | 约束 | 具体表现 |
|---|---|---|
| 1 | **`guard` 是同步的** | guard 里**写不了文件**、跑不了 async ⇒ D1 结论只能走「内存镜像 + 同步算哈希比对」 |
| 2 | **`lib/*.js` 改动必须重启 DSH** | 切 `mode` **不需要**；但改代码**必须**。这使得每个批次都要**停机一次** |
| 3 | **审计链是只追加的** | 一旦写入**不可撤销** ⇒ 任何「为了测试」的动作都会**永久留在链上** |

> 🔴 **约束 3 引出了本项目最重要的一条纪律**：
> **不许为了「验证」而推进业务状态、或编造业务理由**。
> 因为最坏结果不是「被拒绝」，而是「**业务状态被真实推进 + 链上永久留一条测试记录**」。

## 四、从日志里能看出的三个模式

### 4.1 模式一：**核证发现的错误，绝大多数在「观测方法」而不在「实现」**

| 类型 | 出现次数（口径：本日志 §二 表格中标注 🔴 的行） |
|---|---|
| 判据/观测方法错了 | 多数 |
| 实现真有缺陷 | 少数（如 0006 `replaced` 抹 `appliedSeq`、0014 D2 不重算 hash、0018 fail-dead、0055 崩溃零输出、0066 B 0 字节、0086 UTC 时区） |

**结论**：**看到异常先怀疑自己的判据**——本项目用 7 天时间、上百次往返证明了这一点。

---

### 4.2 模式二：**「我给的命令/仪器」也经常是错的**

| # | 事件 |
|---|---|
| 0026 | 自己的仪器**对坏样本说 OK** |
| 0027 | 自己的 **shell 命令骗了我** |
| 0037 | **我给的命令本身不成立** |
| 0052 | **仪器命令下错** |

**结论**：**仪器本身也是被测对象**。写判据的人必须把自己的命令也当成「可能有 bug 的东西」来验。

---

### 4.3 模式三：**自我纠正的次数在持续累积**

| 口径 | 数字 |
|---|---|
| Claude Code 承认的错误 | 累计至**第 28 次**（`_inbox/0052`） |
| WorkBuddy 承认的错误 | 累计至约**第 23 次**（`_inbox/0043`） |

> ⚠️ **如何解读这个数字**：**它不是「项目质量差」的证据**。
> 这些错误绝大多数**在交付前就被核证抓住并改正了**——也就是说，**机制在生效**。
> 真正危险的是**没被记录下来的错误**。
