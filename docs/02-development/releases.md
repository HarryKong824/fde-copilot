## 二、实际使用的版本管理手段（三套并行）

### 2.1 手段一：改动前快照（**主力手段**）

```
_snapshots/<日期><字母>-before/      ← 改动【前】整目录复制过去
_snapshots/<日期>-pre-<批次>/        ← 批次开工前的快照
```

**实测存在 35 项**（口径：`_snapshots/` 目录下的条目，含 31 个目录 + 4 个状态文件备份）。

**命名规律**：

| 形态 | 示例 | 含义 |
|---|---|---|
| `<日期>` | `2026-09-24` | 当天首次快照 |
| `<日期><字母>-before` | `2026-09-24c-before` | 当天第 3 次改动前 |
| `<日期>-pre-<批次名>` | `2026-09-28-pre-d5-live` | 某批活验开工前 |
| `<日期>-p<编号>-before` | `2026-09-27-p111-before` | 对应 `_inbox/0027`（P1-11） |

> ✅ **这套做法的优点**：**能逐文件 SHA-256 对拍**。
> 本项目用它验证「改前 / 改后」的差异**恰好等于自报的改动数**——这是 `git diff` 的替代品。

---

### 2.2 手段二：状态文件的**带版本号备份**

```
state.yaml.phase11-rev28.bak
state.yaml.phase11-rev30.2026-09-26T02-03-23
state.yaml.phase6-rev29.2026-09-25T13-43-17
state.yaml.phase6-rev31.2026-09-26T02-33-59
```

**命名规律**：`state.yaml.<阶段>-rev<revision>.<ISO 时间戳>`

| 字段 | 来源 |
|---|---|
| `phase11` / `phase6` | `state.yaml` 里的 `current_phase` |
| `rev28` / `rev29` / `rev30` / `rev31` | `state.yaml` 里的 **`revision` 字段** |
| ISO 时间戳 | 备份时刻 |

> ✅ **这套做法的巧妙之处**：它直接**复用了系统自己的 `revision` 计数器**。
> `revision` 是工具每次成功写入时 +1 的字段——**所以备份文件名天然带着版本序号**。

> 🔴 **⚠️ 但必须注意一条纪律**（来自 `_inbox` 的实测教训）：
> **恢复 `state.yaml` 时，必须保留 `revision` 和 `updated_at` 的原值**。
> 那是**工具写的计数器**，手工改它 = **伪造版本历史**。

---

### 2.3 手段三：源 ↔ 部署副本对拍

```bash
node _deploy_diff.mjs      # 期望输出：ALL_MATCH
```

**作用**：工作区里的**源目录**与 DSH 里的**部署副本**是两份文件。
这个脚本逐文件算 SHA-256 对拍，确保「改了源但忘了部署」会被抓出来。

| 项 | 说明 |
|---|---|
| **对拍域** | **14 个文件** |
| **⚠️ 域里包含什么** | **包含 `README.md`**，不只是 `lib/*.js` |
| **实测踩过的坑** | 只改了源 README 没同步副本 ⇒ 报 `HAS-DIFF`，而 14 个里**只有这一处**不一致 |
| **为什么危险** | 极易被误读成「代码没同步」 |

> ⚠️ **README 不参与运行时** ⇒ 补一次 `cp` 即可，**不必重启 DSH**。

---

### 2.4 三套手段覆盖了什么

| 能力 | 快照 | 状态文件备份 | 对拍 |
|---|---|---|---|
| 回答「改之前长什么样」 | ✅ | ✅（仅状态） | ❌ |
| 回答「源和现场是否一致」 | ❌ | ❌ | ✅ |
| 逐文件 SHA-256 校验 | ✅ | ✅ | ✅ |
| **回答「某一行是谁改的」** | ❌ | ❌ | ❌ |
| **回答「哪些改动属于同一次发布」** | ⚠️ 靠命名 | ⚠️ 靠命名 | ❌ |
| **回滚** | ✅ 手工复制 | ✅ 手工复制 | ❌ |

## 三、实际的「发布」是怎么发生的

本项目的「发布」不是 `git tag` + 打包，而是这套固定动作：

```
① 存快照        cp -r <插件>  _snapshots/<日期>-before/<插件>
② 改代码
③ 跑回归        bash _run_all_tests.sh     → 期望 ALL-TESTS-GREEN
④ 对拍          node _deploy_diff.mjs      → 期望 ALL_MATCH
⑤ 部署          cp -r  到  <DSH_HOME>\profiles\web\node_modules\
⑥ 重启 DSH      ⚠️ 必须——改 lib/*.js 不重启等于没改
⑦ 活验          驱动真实模型调工具，看链上是否出现预期记录
```

**这七步就是本项目的「release pipeline」**，只是它是**手工执行**的。

## 五、改成 git 之后**本可以避免什么**（如实记录）

| 本项目实际发生 | 有 git 的话 |
|---|---|
| 手工存 35 个快照，**全量复制**，磁盘占用大 | `git commit` 只存差异 |
| 改了 14 个文件后**无法逐行追溯**「谁在什么时候改的」 | `git blame` |
| **`_deploy_diff` 报 `HAS-DIFF` 却看不出改了什么** | `git diff` 一眼看出 |
| 无法回答「某个改动**属于哪次发布**」 | `git log` / tag |
| 出问题靠手工复制回滚 | `git revert` |
| 六个源文件被快照覆写后**无从对比**（`_snapshots/2026-09-24c-before/` 与 `dsh-fde-phase/lib/tools.js` 只能手工 diff） | 同上 |

## 六、给接手者的建议（**本次归档的落地项**）

| # | 建议 | 优先级 |
|---|---|---|
| 1 | **`git init` 并做首次提交**，把 `_snapshots/` 加进 `.gitignore`（它的历史价值已被 git 取代） | 🔴 高 |
| 2 | 四个插件**各自从 `0.0.1` 起正式编号**，每次改动 bump patch | 🟠 中 |
| 3 | 把 §三 那七步**写成脚本**（`release.sh`），避免手工漏步 | 🟠 中 |
| 4 | 给「部署态」打 tag（如 `deployed-2026-09-29`），记录**现场装的到底是哪一版** | 🟠 中 |
| 5 | `CHANGELOG.md` 按 Stage/批 补写历史（素材就在 `_inbox/`，本套文档已整理） | 🟡 低 |

> 📌 其中 **#1 已在本交付仓库中执行**——本交付目录就是一个准备好的 git 仓库结构。

---

## 七、一句话总结

> **本项目用「快照 + 状态备份 + 源副本对拍」三套手工手段，替代了 7 天的版本控制，
> 并做到了「改动可逐一比对」；但它做不到「逐行追溯」和「按发布分包」。
> 这 35 个快照不是落后，是**在缺少版本控制时，用纪律换来的可追溯性**——
> 而这份可追溯性，现在已经可以直接交给 git 了。**
